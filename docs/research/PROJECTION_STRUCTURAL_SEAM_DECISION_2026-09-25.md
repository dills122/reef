# Projection structural seam decision — 2026-09-25

Status: architecture recommendation, not implementation or a throughput claim. Source: merged `56b89fda7df2e07c321a7d357532641a0fe309d7` (PR #359). No new load or infrastructure was run for this memo.

## Decision

Split by **operational read contract versus audit timeline**, rather than treating the existing `status/fill` and `timeline/payload` SQL functions as independently safe workers. Put command results, orders, executions, trades, and complete own-order lifecycle in one ordered operational projection. Put venue-batch timeline headers and payload access in an independently checkpointed audit projection; preserve direct admin and other non-venue events through their own durable source and read path. Market state remains a downstream operational projection with its own freshness proof. First make lifecycle derivable from compact canonical outcome facts without reading `runtime_events`; then separate audit persistence. Keep the present full transaction and mixed-event read routes as rollback paths until exact business, audit, and replay parity passes.

This is a capacity hypothesis. Running two workers against the same PostgreSQL instance **does not remove rows or WAL**. The likely capacity mechanisms are (a) removing audit writes and indexes from the operational commit's critical path, (b) avoiding repeated lifecycle scans of historical executions and events, (c) reducing duplicated audit payload storage where canonical facts are sufficient, and (d) only if needed, placing the audit projection on a separately provisioned PostgreSQL instance. Each must earn its own matched full-pipeline result. Do not claim 10k from stage-only or postdrain completion.

## Evidence boundary and present path

The historical sustained full-projection pass is H4/C4 at about 2,500 accepted commands/s for 300s. C5/H1 prove approximately 10,000/s for venue-core materialization **with projections disabled**, not the full pipeline. On the merged C43 baseline, the fresh c-32, six-materializer, 16-projector-owner, 10k-offered, 300s fixture accepted/direct-acked/materialized 2,992,504 (9,973.99/s). A **later** projector collection counted 2,967,975 (9,892.24/s) and 26,029 lag. Those snapshots are not simultaneous; the frozen full-pipeline checker failed, including downstream freshness/cohort authority, and 20% drain margin is unproven. After drain, source and projection both reached 2,992,504, all 16 frontiers were contiguous, queues emptied, and rebuilds matched 2,465,524 lifecycle and 64 market rows. C42 also failed at 9,885.93/s projected with 34,201 lag. C43's index ablation lowered projection WAL/accepted from C42's 5,820.59 to 5,658.69 bytes (about 2.8%); its 6.31/s projector-rate difference does not establish a throughput gain because intake and sampler timing differed. See [C42–C43 ledger](../THROUGHPUT_BASELINES.md#c42--lock-only-dirty-conflicts-write-target-removed-full-pipeline-timed-fail) and the [active plan](../PROJECTION_THROUGHPUT_SCALING_PLAN.md#september-25-canonical-batch-insert-diagnostic).

Current path, verified in source:

```text
boundary -> durable command acknowledgement (202 only after ingress ack)
  -> deterministic venue/session/instrument lane in Go engine
  -> durable VenueEventBatch -> compact canonical Postgres materializer commit
  -> per-partition canonical_command_outcomes and immutable result/batch facts
  -> 16 projection owners select contiguous partition-sequence members
  -> batch claim + normalized SQL + watermark completion in one transaction
  -> dirty order queue -> lifecycle state -> dirty instrument queue -> market snapshot
  -> API: canonical command lookup; projected own orders/fills/trades/events/market
```

Same-store `runtime_project_canonical_command_outcome_members` claims exact ordered members and invokes `runtime_persist_submit_outcomes`; separated-store Kotlin does the equivalent within one projection transaction. The full SQL wrapper calls status/fill then timeline/payload serially before watermark advancement. Status/fill writes `submit_results`, `orders`, `executions`, `trades`, and lifecycle invalidations. Timeline writes `runtime_events` and `runtime_event_payloads`; deterministic events use stream sequence and ordinal, while legacy events use the trace allocator. Lifecycle refresh subsequently aggregates executions and events for each dirty order; it uses `OrderModified`, `OrderCancelled`, and `OrderRejected` timeline facts. Market refresh reads lifecycle state. Thus today's `command-status` ablation is **not** an independent own-order-fresh gate. Sources: [claim/membership SQL](../../scripts/dev/db/migrations/runtime/0050_projection_batch_claims.sql), [full wrapper](../../scripts/dev/db/migrations/runtime/0041_deterministic_timeline_projection_sequence.sql), [active status/fill](../../scripts/dev/db/migrations/runtime/0059_trade_replay_and_parse.sql), [timeline/payload](../../scripts/dev/db/migrations/runtime/0043_runtime_event_payload_cold_table.sql), [lifecycle refresh](../../scripts/dev/db/migrations/runtime/0052_projection_dirty_serialization.sql), and [Kotlin separated-store flow](../../services/platform-runtime/src/main/kotlin/com/reef/platform/infrastructure/persistence/PostgresRuntimePersistence.kt).

The venue projector is not the only event producer. `AdminApplicationService.emitAudit` and `PlatformApi.recordAdminEvent` (also used by protective-control auditing) call `saveEvent`; compatibility persistence can call `saveEvents`. PostgreSQL `saveEvents` writes directly to `runtime_events`/`runtime_event_payloads` and allocates trace sequences. `eventsForOrder`, `eventsForTrace`, `events`, and `recentEvents` all query that mixed table; current `/orders/{id}/events`, `/traces/{id}/events`, and `/events` routes therefore see non-venue events. A venue-only audit stage cannot replace those reads. Sources: [admin producer](../../services/platform-runtime/src/main/kotlin/com/reef/platform/application/admin/AdminApplicationService.kt), [API producer](../../services/platform-runtime/src/main/kotlin/com/reef/platform/api/PlatformApi.kt), [direct persistence and reads](../../services/platform-runtime/src/main/kotlin/com/reef/platform/infrastructure/persistence/PostgresRuntimePersistence.kt), and [HTTP routes](../../services/platform-runtime/src/main/kotlin/com/reef/platform/api/PlatformHttpServer.kt).

C30's nested diagnostic measured 6,624 full persistence calls at 604.5ms mean; its status/fill statement averaged 357.8ms and 8.93GB tracked WAL, timeline/payload 144.7ms and 6.62GB WAL, and the separate submit-result conflict check 43.0ms. Parent/child times overlap and cannot be added or interpreted as a wall-clock saving from a split. The aged C32 stage-only probe processed synthetic mixed outcomes at about 53k/s with 16 writers and 2.36–2.37KB WAL/outcome, without timeline, lifecycle/market workers, or live contention. It disproves a simple claim that isolated status/fill SQL alone has a measured 10k capacity ceiling. C42 still recorded about 19.96 million projection inserts and 17.47GB projection WAL despite eliminating dirty-queue tuple updates. The stronger observed problem is concurrent full-pipeline write amplification and freshness residence, not one demonstrably slow table. [C30 raw aggregate](../evidence/projection-canonical-sql-c30-2026-09-25.json), [aged stage probe](PROJECTION_STATUS_FILL_AGED_PROFILE_2026-09-25.md), [C28 same-prefix timing](../THROUGHPUT_BASELINES.md#c28--same-prefix-marker-timing-full-projection-10k-diagnostic).

## Ranked structural options

| Rank | Option | Why / decision |
| --- | --- | --- |
| 1 | Operational read model plus independently checkpointed audit model, with compact lifecycle facts from canonical outcomes | Separates actual read/freshness ownership and removes audit commits from operational latency. Required dependency repair makes the split correct. **Choose, staged.** Extra stores alone do not reduce total write work. |
| 2 | Thin venue-audit event locator with payload reconstructed from canonical facts | Potentially removes one full JSON copy and payload-table insert per venue event; could beat physical splitting for total WAL. **Conditional next slice**, only after proving canonical data and retention are self-contained for every affected public timeline/read/replay case, including legacy batches and trace metadata. Direct events retain their own payload authority. No measured savings yet. |
| 3 | Per-order incremental lifecycle maintenance only | Avoids repeated historical execution/event aggregation; C25 shows recompute/write, not dirty claims, dominates isolated lifecycle time. Could increase hot-row updates and lock contention. Trial only with exact parity and full-system gate. |
| 4 | Run current status/fill and timeline functions as separate workers/checkpoints | Removes serial wait but preserves all writes, and current lifecycle reads timeline. Unsafe as an own-order-fresh claim until the dependency is replaced or a join barrier is enforced. |
| 5 | More owners, index drops, or dirty-queue rewrites | C31 rejected an unused-index drop; C41–C43 and C25 show these bounded changes did not clear full-pipeline capacity. Retain valid cleanups, but do not lead with another such treatment. |

No option has a supported numerical 10k or 12k capacity forecast. C30's 8.93/6.62GB WAL attribution describes *where* writes occurred, not removable bytes. Removing audit payload duplication has a calculable upper bound only after measuring how much of the 6.62GB is actual payload versus headers, indexes, and transaction overhead.

## Target contract and failure behavior

**Authority and keys.** Canonical `VenueEventBatch` and `canonical_command_outcomes` remain immutable replay/audit authority **for venue outcomes**; direct admin events currently have a different source and must not be represented as venue members. No new work goes onto the durable acceptance path. Keep the existing event-stream + partition-ID + contiguous `stream_sequence` membership and batch payload hash. Within each partition, apply effects in sequence order. Use the same venue-session/instrument lane as matching where metadata exists. Coalesce all order effects within a batch, but never reorder a given order's commands/fills. A maker/taker fill affecting an older order must use the canonical event's actual order IDs, exact numeric quantities, and deterministic event ordinal. Validate that both affected orders map to the expected lane; if not, introduce an explicit order-key sequencer/merge rule and test it before incremental maintenance. Do not infer order causality from timestamp or UUID sort order.

**Operational transaction.** For a claimed canonical member set, write command result, accepted order, executions, trades, and compact per-order lifecycle transition/accumulator in one PostgreSQL transaction; advance `operational` partition watermarks and complete the stage-specific D-055 claim only after those effects commit. Apply one order-state update per affected order per batch where parity allows, carrying original/current quantity, exact cumulative fill, latest modification, terminal flags, and last-event key. Preserve current text and numeric shadow-field semantics and complete terminal zero remainder. Feed market invalidations in that same transaction; market snapshot/level maintenance has its own frontier and cannot claim coverage until affected operational transactions and market invalidations commit. Initially keep market's existing reference SQL for parity; do not introduce a book-delta algorithm in the same slice.

**Audit transaction and replay.** Independently claim venue canonical membership under `audit` stage identity. Insert event header and payload (or later a proven locator) and advance the venue-audit per-partition watermark atomically. `event_id` uniqueness must mean *identical semantic content*, not merely an occupied key. Current timeline and direct `saveEvents` writes use `ON CONFLICT (event_id) DO NOTHING` for headers and payloads; source inspection establishes a possible conflicting-content skip, **not observed corruption**. Compare all semantic header fields, typed modify facts, and full payload digest/bytes on conflict; compare the assigned sequence for deterministic stream events. Identical replay is a no-op, mismatch raises a permanent conflict and leaves the affected frontier unchanged. Event header without required payload or vice versa fails closed, except explicitly migrated legacy inline-payload rows with a verified equivalence rule. Add event identity/version to the batch claim contract rather than repurposing a `full` identity.

For **legacy events without `streamSequence` and direct `saveEvents`**, the current trace allocator advances before an insert can discover an existing `event_id`. Use one transaction to lock event IDs in stable order, read existing header/payload content, and discard identical IDs **before** counting new events or allocating trace sequences. Allocate only for novel IDs in stable per-trace order; reuse an existing event's stored sequence when validating a duplicate. Serialize concurrent absent-ID claims (for example with transaction-scoped event-ID advisory locks) before that preflight, then retain the unique constraint as the final race guard. A lock hash collision may serialize unrelated events but must not equate their identities. Backfill or verify legacy event identity from stored header and payload before switching this path. Test an identical ID under a different batch claim, concurrent same-ID arrivals, mixed new/duplicate IDs on one trace, changed content, allocator continuity, and ambiguous commit. The hot canonical stream-sequence path keeps its deterministic assignment.

**Non-venue audit source.** Inventory every direct and compatibility event producer and every timeline read route before cutover. Keep `runtime_events` as the durable source and existing read route for non-venue events during shadow rollout; venue-batch checkpoints do not prove their completeness. Use an append-only direct-audit journal in the existing runtime PostgreSQL for future non-venue writes, with `event_id` uniqueness, full envelope/payload, producer/source kind, trace sequence, and content digest. Populate it in the same transaction as each direct `saveEvents` write; retain today's admin-mutation/audit failure semantics and test them. Backfill retained direct events from the mixed table by **verified provenance**, compare bytes/order/counts, and leave any unclassifiable historical row on the legacy read route. Stream or replay that journal to the audit read store with its own contiguous source frontier and error state. A new source kind and any stronger admin atomicity need an explicit contract and migration. If equivalent non-venue authority, backfill, and merged ordering cannot be proved, keep **all mixed timeline reads** on the legacy table rather than silently returning a venue-only subset. Do not retire that table while it remains the sole durable source for direct events.

**Frontiers and reads.** Store `projection_epoch`, stage, event stream, partition, and last contiguous sequence for venue stages; represent absent partitions and errors explicitly. Track non-venue audit progress against its own durable source, not the venue partition vector. A public command lookup continues to prefer canonical command outcomes, so it does not wait for audit. Route own-order, fill, trade, and current-market reads to the operational store; route mixed order/trace/event-list reads to the new audit store **only after** both source classes and their ordering are proved there. Any response combining lifecycle and timeline facts is covered only through the **componentwise minimum** of operational and venue-audit frontiers for its venue source partitions, plus the applicable non-venue frontier. Never combine a newer order state with an older event trail while labelling the whole response fresh. Return the existing source/lag metadata and apply the current route's freshness/error behavior; do not silently change a public route or promise stronger consistency than the old one. Cross-database reads do not share an MVCC snapshot; a common prefix plus as-of filtering and a verified read token are required before a combined-read cutover. Keep that read on the legacy store until this contract is proved. Market freshness additionally needs a committed operational prefix and a drained/covered market queue; an empty unlogged queue alone is not proof after restart.

**Backpressure and recovery.** Preserve `control-room-fresh` versus `venue-core` policy. Control-room freshness samples both stage lags plus lifecycle/market coverage; venue-core continues to report projection lag while gating durable worker lag. In either mode, reject *before* durable ingress if finite canonical retention, disk, or replay horizon would be exceeded; never emit 202 until durable acceptance itself is acknowledged. A stalled audit stage is an explicit full-pipeline failure, not permission to call operational-only throughput “full.” On crash, recover each stage from its last committed contiguous canonical frontier and D-055 claim; ambiguous commits must read completed claims rather than reapply effects. Rebuild unlogged dirty queues from canonical/frontier gaps after PostgreSQL restart and invalidate freshness proofs across postmaster generations until verified. Permanent hash/content mismatches quarantine the member, alert, and stop that partition's frontier; no skip, overwrite, or dead-letter-and-advance. Transient serialization/deadlock retries remain bounded by the immutable retry deadline. Failed projection writes do not undo canonical acceptance; they create visible lag and backpressure.

**Placement and rollout.** Keep canonical tables in canonical Postgres. Begin with operational and venue-audit schemas/claims/frontiers in the existing projection instance to prove semantics; keep the direct-audit journal in runtime PostgreSQL and its legacy mixed read route until complete migration is verified. A separate audit PostgreSQL **instance**, with its own WAL/storage budget, is a later topology experiment; a second database in the same instance shares core I/O resources. Preserve local Compose single-instance support. Build a shadow operational projection from canonical facts, compare full rows and frontiers, then switch individual operational API read adapters only after parity. Build venue and non-venue audit shadows independently and prove their merged read order before switching any mixed timeline route. Retain the old full projector and read routing through the rollback window, but do not run synchronous dual writes on intake. Rollback is a routing/worker switch to the old projection if its frontier is current; otherwise replay the old venue projection from canonical authority and the non-venue journal before declaring rollback complete. Version the projection epoch and migrations; do not rewind a watermark in place or reuse a stage name for different effects. Only retire old tables after a separate retention/rebuild decision.

## Small implementation slices and one decisive gate each

Use the C43 fixture, source commit/image manifest, six materializers, 16 owners, 64 instruments, 300s/10k offered, database settings, observer cadence, and fixed collection points as the comparison template. Record the actual read-load setting and any unavoidable code/topology/hardware change explicitly; preserve failed setup and runs under new ledger IDs. The C43 raw artifact path is host-local and may be unavailable; the ledger and hashes remain the authority. Do not depend on the test droplet. Each material slice gets focused fault/parity tests and **one matched 10k/300s treatment against a fresh control** as a diagnostic decision about that slice. These individual runs do not promote the final architecture.

0. **Checker authority and producer inventory, before split qualification.** Extend `scripts/dev/stress.mjs` reporting, `scripts/dev/do-benchmark-check.mjs`, and `scripts/dev/full-projection-headroom.mjs` to understand `projection_epoch`, stage, event stream, and partition. Today's `streamAckProjector` delta, frozen checker, and headroom helper observe one `full` stage and one watermark; they cannot attest two independent stages. Keep the frozen legacy profile and thresholds for the unchanged control, add a versioned split profile, and validate its instrumentation under the existing perturbation rule before using it for capacity claims. Each of `operational` and venue `audit` must independently cover the **same accepted canonical member cohort**, with exactly one contiguous frontier per source partition at each prescribed collection point; never sum their counts. Reject missing, duplicate, stale-epoch, wrong-stream, or gapped stage observations, generation drift, unbounded lag, and stage-specific failed/retried/deadlocked work under the existing limits. Retain lifecycle, market, read-load, sampler-clock, and full-reference checks. Count non-venue events against their **own journal cohort/frontier**, not accepted venue commands. Inventory every direct writer and mixed read route; add fixture tests that omit or corrupt each stage, alter epoch/generation, and omit a direct event. Decisive gate: known-good and known-bad synthetic reports classify correctly, the unchanged full profile remains equivalent on a fresh control, instrumentation perturbation passes, and the producer/read inventory is complete. Tooling alone makes no throughput claim.
1. **Conflict guard and stage identity.** Add equal-content event/payload replay checks, stage/epoch identity, and contiguous-frontier tests without changing full-path routing. Test same-ID same-content retry across different claims, changed header/payload/typed fact, missing payload, direct `saveEvents`, concurrent absent-ID arrivals, mixed novel/duplicate trace events, trace allocator continuity, ambiguous commit, and rollback-before-watermark. Diagnostic gate: fresh C43-shaped full run versus fresh unchanged control, requiring exact counts, business/replay equality, no conflict false positives, and no material regression in the frozen timed/freshness measures. A failure keeps the old full path.
2. **Compact operational lifecycle derivation.** Implement canonical-derived per-order transitions behind a shadow projection; compare every lifecycle business field (including numeric shadows) to a quiesced full rebuild for submit/reject/cancel/modify/partial fill/trade replay, interleaved maker/taker fills, conflicting retries, and restart. Diagnostic gate: one fresh matched 10k/300s full-pipeline run with the same audit path, requiring the 5s lifecycle, 10s market, and 30s tail bounds, exact frontiers/reference, and an improved operational residence/cost profile. If per-order update contention or WAL rises without better full-pipeline freshness, revert this slice.
3. **Independent venue audit checkpoint and direct-event migration.** Keep existing event/payload rows initially; move venue audit writes out of the operational transaction. Add the transactional non-venue journal and provenance-checked backfill before any mixed read switch. Test ahead/behind stages, event conflict quarantine, crash between commits, independent venue/direct replay, admin failure semantics, and mixed order/trace/global read parity including pagination and ordering. Diagnostic gate: matched 10k/300s full-pipeline run using the split checker at fixed collection points and requiring **both** venue stages' exact cohort/freshness, direct-event cohort completeness, lifecycle/market bounds, zero gaps, and full rebuild/read parity. An operational-only pass is diagnostic, not promotion; failed provenance keeps mixed reads on the legacy route.
4. **Audit storage reduction, then placement only if necessary.** Prove canonical payload/trace self-containment for venue events and replace duplicate venue payload rows with an indexed locator or bounded archive fetch behind unchanged read semantics; keep immutable event identity and retention. Test old/new payload byte parity, trace/order pagination and ordering, archive expiry, corruption, and point-read latency. Diagnostic gate: one fresh matched full-pipeline 10k/300s comparison showing lower audit rows/WAL/bytes per accepted command **and** unchanged read/freshness/replay results. If still below target, test a separate audit instance under a stated fixed total CPU/RAM/I/O budget; its one matched diagnostic gate is the same full-pipeline run, explicitly attributing the topology/resource change rather than claiming software efficiency.

**Final promotion gate, after the last material change.** Run the repository's full qualification suite on the final candidate image and configuration, including current-image full-reference/rebuild parity, freshness and recovery, warm and aged state, prescribed read load, and **three separate measured drains at ≥20% headroom** using the established drain method. At each frozen measurement boundary, accepted/direct-acked/materialized and each of the operational and venue-audit projected counts/frontiers must independently match the exact canonical cohort; the non-venue journal and new audit read store must match their own source cohort. Require no failed/exhausted retries, deadlocks, sequence holes, or business/replay mismatch; lifecycle/market/timeline coverage and sampler authority must pass under the versioned split checker without relaxing C43's legacy thresholds. Record each drain and failure separately in the throughput ledger. Distinguish measured drain slope from a conservative coverage bound and from postdrain equality. If any stage misses exact freshness or any of the three drains fails, the architecture has not met the stated goal.

## Assumptions and open decisions

- The canonical outcome plus retained command metadata can reproduce every venue-generated event's payload and trace fields. This must be proved before audit locator storage or shorter retention; older compatibility batches may require immutable backfill.
- Current per-instrument lane ownership is sufficient for both sides of each fill. Verify actual cross-partition order touches; if present, specify deterministic order-key sequencing before incremental lifecycle.
- The current `runtime_events`/payload tables are rebuildable read projections for venue outcomes but remain durable source material for direct admin and protective-control events until their separate journal is complete. Post-trade canonical event history and public audit requirements may have different ownership and must not be pruned by this plan.
- C43's full-pipeline gap is small in *rate* but has no proven 20% reserve; a merely 0.1–1% improvement is not the target. The exact point where PostgreSQL write/WAL contention or lifecycle recompute becomes the limiter after separation is unknown.
- Decide the retention/replay horizon, combined-read consistency token, audit-instance resource budget, and measured read-latency SLO before cutting over. If those choices cannot preserve current API behavior, keep the legacy full read path while still measuring the shadow projection.
