# Projection structural seam decision — 2026-09-25

Status: revised architecture research and conditional decision, not implementation or a throughput claim. Source: merged `56b89fda7df2e07c321a7d357532641a0fe309d7` (PR #359); this critique is on PR #362. No new load or infrastructure was run for either memo revision.

## Decision

**Do not commit to an operational/audit worker or database split yet.** Treat it as a conditional read-ownership seam whose semantic shape is plausible, but whose capacity benefit and migration cost are unproved. First repair replay conflicts, prove exact event/lifecycle derivation, and measure the concurrent full-pipeline cost of lifecycle recomputation and normalized writes. Trial a one-store write-reduction/lifecycle treatment with the full projector still intact. Choose independent audit checkpointing only if that matched treatment leaves a measured audit commit or freshness dependency that a split can remove without increasing total resource pressure. An audit locator or separate instance remains a later, separately justified experiment. This is a material change from the original recommendation to build the split as the next structural slice.

The candidate capacity mechanisms are distinct: (a) less repeated lifecycle work, (b) fewer normalized rows/index writes or bytes per accepted command, (c) a shorter operational commit through independent audit persistence, and (d) more physical I/O capacity through another instance. Two workers on one PostgreSQL instance **remove no rows or WAL** and can increase contention. C30's nested SQL time cannot price a split, while the aged C32 stage-only result cannot clear the full pipeline. Each mechanism needs its own matched full-pipeline evidence. Do not claim 10k from stage-only or postdrain completion.

## Evidence boundary and present path

The historical sustained full-projection pass is H4/C4 at about 2,500 accepted commands/s for 300s. C5/H1 prove approximately 10,000/s for venue-core materialization **with projections disabled**, not the full pipeline. In the C43 failed full-pipeline diagnostic, the fresh c-32, six-materializer, 16-projector-owner, 10k-offered, 300s fixture accepted/direct-acked/materialized 2,992,504 (9,973.99/s). A **later** projector collection counted 2,967,975 (9,892.24/s) and 26,029 lag. Those snapshots are not simultaneous; the frozen full-pipeline checker failed, including downstream freshness/cohort authority, and 20% drain margin is unproven. After drain, source and projection both reached 2,992,504, all 16 frontiers were contiguous, queues emptied, and rebuilds matched 2,465,524 lifecycle and 64 market rows. C42 also failed at 9,885.93/s projected with 34,201 lag. C43's index ablation lowered projection WAL/accepted from C42's 5,820.59 to 5,658.69 bytes (about 2.8%); its 6.31/s projector-rate difference does not establish a throughput gain because intake and sampler timing differed. See [C42–C43 ledger](../THROUGHPUT_BASELINES.md#c42--lock-only-dirty-conflicts-write-target-removed-full-pipeline-timed-fail) and the [active plan](../PROJECTION_THROUGHPUT_SCALING_PLAN.md#september-25-canonical-batch-insert-diagnostic).

Current path, verified in source:

```text
boundary -> durable command acknowledgement (202 only after ingress ack)
  -> deterministic venue/session/instrument lane in Go engine
  -> durable VenueEventBatch -> compact canonical Postgres materializer commit
  -> per-partition canonical_command_outcomes and immutable result/batch facts
  -> 16 projection owners select contiguous partition-sequence members
  -> batch claim + normalized SQL + watermark completion in one transaction
  -> dirty order queue -> lifecycle state -> dirty instrument queue -> market snapshot
  -> API: canonical command lookup; projected own orders/fills/trades/events/market
```

Same-store `runtime_project_canonical_command_outcome_members` claims exact ordered members and invokes `runtime_persist_submit_outcomes`; separated-store Kotlin does the equivalent within one projection transaction. The full SQL wrapper calls status/fill then timeline/payload serially before watermark advancement. Status/fill writes `submit_results`, `orders`, `executions`, `trades`, and lifecycle invalidations. Timeline writes `runtime_events` and `runtime_event_payloads`; deterministic events use stream sequence and ordinal, while legacy events use the trace allocator. Lifecycle refresh subsequently aggregates executions and events for each dirty order; it uses `OrderModified`, `OrderCancelled`, and `OrderRejected` timeline facts. Market refresh reads lifecycle state. Thus today's `command-status` ablation is **not** an independent own-order-fresh gate. Sources: [claim/membership SQL](../../scripts/dev/db/migrations/runtime/0050_projection_batch_claims.sql), [full wrapper](../../scripts/dev/db/migrations/runtime/0041_deterministic_timeline_projection_sequence.sql), [active status/fill](../../scripts/dev/db/migrations/runtime/0059_trade_replay_and_parse.sql), [timeline/payload](../../scripts/dev/db/migrations/runtime/0043_runtime_event_payload_cold_table.sql), [lifecycle refresh](../../scripts/dev/db/migrations/runtime/0052_projection_dirty_serialization.sql), and [Kotlin separated-store flow](../../services/platform-runtime/src/main/kotlin/com/reef/platform/infrastructure/persistence/PostgresRuntimePersistence.kt).

The venue projector is not the only event producer. `AdminApplicationService.emitAudit` and `PlatformApi.recordAdminEvent` (also used by protective-control auditing) call `saveEvent`; compatibility persistence can call `saveEvents`. PostgreSQL `saveEvents` writes directly to `runtime_events`/`runtime_event_payloads` and allocates trace sequences. `eventsForOrder`, `eventsForTrace`, `events`, and `recentEvents` all query that mixed table; current `/orders/{id}/events`, `/traces/{id}/events`, and `/events` routes therefore see non-venue events. A venue-only audit stage cannot replace those reads. Sources: [admin producer](../../services/platform-runtime/src/main/kotlin/com/reef/platform/application/admin/AdminApplicationService.kt), [API producer](../../services/platform-runtime/src/main/kotlin/com/reef/platform/api/PlatformApi.kt), [direct persistence and reads](../../services/platform-runtime/src/main/kotlin/com/reef/platform/infrastructure/persistence/PostgresRuntimePersistence.kt), and [HTTP routes](../../services/platform-runtime/src/main/kotlin/com/reef/platform/api/PlatformHttpServer.kt).

C30's nested diagnostic measured 6,624 full persistence calls at 604.5ms mean; its status/fill statement averaged 357.8ms and 8.93GB tracked WAL, timeline/payload 144.7ms and 6.62GB WAL, and the separate submit-result conflict check 43.0ms. Parent/child times overlap and cannot be added or interpreted as a wall-clock saving from a split. The aged C32 stage-only probe processed synthetic mixed outcomes at about 53k/s with 16 writers and 2.36–2.37KB WAL/outcome, without timeline, lifecycle/market workers, or live contention. It disproves a simple claim that isolated status/fill SQL alone has a measured 10k capacity ceiling. C42 still recorded about 19.96 million projection inserts and 17.47GB projection WAL despite eliminating dirty-queue tuple updates. The stronger observed problem is concurrent full-pipeline write amplification and freshness residence, not one demonstrably slow table. [C30 raw aggregate](../evidence/projection-canonical-sql-c30-2026-09-25.json), [aged stage probe](PROJECTION_STATUS_FILL_AGED_PROFILE_2026-09-25.md), [C28 same-prefix timing](../THROUGHPUT_BASELINES.md#c28--same-prefix-marker-timing-full-projection-10k-diagnostic).

## Decision table and structural options

| Priority | Option | Capacity mechanism and evidence | Decision / limiting proof |
| --- | --- | --- | --- |
| First trial | Reduce write amplification within the existing full projector | Fewer normalized rows/index bytes/commits per outcome could lower shared I/O; C42/C43 show large residual write volume, not which rows are safely removable. | **Measure and prototype first.** Retain canonical and externally visible facts, unchanged mixed reads and D-055 atomicity. Require actual full-pipeline WAL/rows and freshness improvement; a thinner table without a replay/retention proof is inadmissible. |
| First trial where causal facts suffice | Incremental per-order lifecycle behind the current full transaction | Avoids rescanning execution and event history; C25 isolated recompute dominates dirty claims, but C26's query-local win failed the hosted freshness criterion. | Test behind an isolated shadow and compare exact business fields, order causality, lock waits and WAL. It can remain an independent downstream worker; moving it into the status/fill commit needs separate evidence. |
| Conditional | Operational read contract plus independently checkpointed venue audit | Can shorten operational commit **after** lifecycle no longer reads timeline; does not reduce total same-instance writes. | Adopt only after a matched full-pipeline result shows audit delay is material, stage-vector authority works, and each stage plus mixed reads has independent source coverage. |
| Conditional storage treatment | Venue event locator/compact payload | May remove duplicate JSON bytes and inserts if canonical facts reconstruct every required event. | Prove byte-for-byte/versioned event and trace reconstruction, point-read SLO, immutable source retention and corruption behavior before a live read or retention change. |
| Conditional placement | Audit on separate PostgreSQL instance | Can buy physical I/O headroom, but adds capacity and cross-store consistency/recovery cost. A second database in the same instance does not isolate WAL/CPU. | Compare under both a fixed **total** resource budget and an explicitly increased budget; label the latter a capacity purchase, not a software throughput gain. |
| Reject as stand-alone fix | Split today's `status/fill` and `timeline/payload` functions; add owners or drop more indexes | Existing lifecycle dependency makes an operational freshness claim false; C31/C41–C43 did not clear the timed gate. | Keep only bounded cleanups with matched evidence and no semantics change. |

No option has a supported numerical 10k or 12k capacity forecast. C30's 8.93/6.62GB WAL attribution describes *where* writes occurred, not removable bytes. Removing audit payload duplication has a calculable upper bound only after measuring how much of the 6.62GB is actual payload versus headers, indexes, and transaction overhead.

## Conditional split contract and failure behavior

The following is a design contract **only if the split gate above passes**. It is not a commitment to implement every stage below. The first trial leaves the existing full projector and API routing in place.

**Authority and keys.** Canonical `VenueEventBatch` and `canonical_command_outcomes` remain immutable replay/audit authority **for venue outcomes**; direct admin events currently have a different source and must not be represented as venue members. No new work goes onto the durable acceptance path. Keep the existing event-stream + partition-ID + contiguous `stream_sequence` membership and batch payload hash. Within each partition, apply effects in sequence order. Use the same venue-session/instrument lane as matching where metadata exists. Coalesce all order effects within a batch, but never reorder a given order's commands/fills. A maker/taker fill affecting an older order must use the canonical event's actual order IDs, exact numeric quantities, and deterministic event ordinal. Validate that both affected orders map to the expected lane; if not, introduce an explicit order-key sequencer/merge rule and test it before incremental maintenance. Do not infer order causality from timestamp or UUID sort order.

**Operational transaction.** If a split is selected, a claimed canonical member set writes command result, accepted order, executions, trades, and sufficient compact per-order lifecycle facts in one PostgreSQL transaction; `operational` watermarks and the stage-specific D-055 claim complete only after its specified effects commit. Whether the final lifecycle row itself belongs in that transaction or in a downstream sequenced maintainer is a measured choice: hot-row locking, WAL and freshness may worsen if forced into every status/fill commit. Coalesce one order-state update per affected order per batch only where parity allows, carrying original/current quantity, exact cumulative fill, latest modification, terminal flags, and last-event key. Preserve current text and numeric shadow-field semantics and complete terminal zero remainder. Market invalidations must be committed with their source facts; market snapshot/level maintenance has its own frontier and cannot claim coverage until affected operational facts and invalidations commit. Initially keep market's existing reference SQL for parity; do not introduce a book-delta algorithm in the same slice.

**Audit transaction and replay.** Independently claim venue canonical membership under `audit` stage identity. Insert event header and payload (or later a proven locator) and advance the venue-audit per-partition watermark atomically. `event_id` uniqueness must mean *identical semantic content*, not merely an occupied key. Current timeline and direct `saveEvents` writes use `ON CONFLICT (event_id) DO NOTHING` for headers and payloads; source inspection establishes a possible conflicting-content skip, **not observed corruption**. Compare all semantic header fields, typed modify facts, and full payload digest/bytes on conflict; compare the assigned sequence for deterministic stream events. Identical replay is a no-op, mismatch raises a permanent conflict and leaves the affected frontier unchanged. Event header without required payload or vice versa fails closed, except explicitly migrated legacy inline-payload rows with a verified equivalence rule. Add event identity/version to the batch claim contract rather than repurposing a `full` identity.

For **legacy events without `streamSequence` and direct `saveEvents`**, the current trace allocator advances before an insert can discover an existing `event_id`. Use one transaction to lock event IDs in stable order, read existing header/payload content, and discard identical IDs **before** counting new events or allocating trace sequences. Allocate only for novel IDs in stable per-trace order; reuse an existing event's stored sequence when validating a duplicate. Serialize concurrent absent-ID claims (for example with transaction-scoped event-ID advisory locks) before that preflight, then retain the unique constraint as the final race guard. A lock hash collision may serialize unrelated events but must not equate their identities. Backfill or verify legacy event identity from stored header and payload before switching this path. Test an identical ID under a different batch claim, concurrent same-ID arrivals, mixed new/duplicate IDs on one trace, changed content, allocator continuity, and ambiguous commit. The hot canonical stream-sequence path keeps its deterministic assignment.

**Non-venue audit source.** Inventory every direct and compatibility event producer and every timeline read route before cutover. Keep `runtime_events` as the durable source and existing read route for non-venue events during shadow rollout; venue-batch checkpoints do not prove their completeness. **Only if mixed reads must move**, establish a lossless direct-event change source. An append-only direct-audit journal is one candidate; compare it with consuming the existing table through a proven ordered change feed before adding a second persistent write. If a journal is selected, put it beside `runtime_events`/`runtime_event_payloads` in the **same PostgreSQL database selected by `projectionConnection()`**, with `event_id` uniqueness, full envelope/payload, producer/source kind, trace sequence, and content digest. Insert direct event and journal row through the **same connection and transaction** in `saveEvents`; never rely on an atomic commit across runtime and projection databases. Test today's actual admin/protective mutation and audit-failure semantics, including the protective caller's caught exception; do not claim new atomicity. Backfill retained direct events from the mixed table by **verified provenance**, compare bytes/order/counts, and leave any unclassifiable historical row on the legacy read route. Stream or replay the source to the audit read store with its own contiguous frontier and error state. If a later topology moves direct-event authority, migrate its writer and source together with explicit cutover and rollback; do not dual-write across stores and call either copy authoritative. A new source kind and any stronger admin atomicity need an explicit contract and migration. If equivalent non-venue authority, backfill, and merged ordering cannot be proved, keep **all mixed timeline reads** on the legacy table. Do not retire that table while it remains the sole durable source for direct events.

**Frontiers and reads.** Store `projection_epoch`, stage, event stream, partition, and last contiguous sequence for venue stages; represent absent partitions and errors explicitly. Track non-venue audit progress against its own durable source, not the venue partition vector. A public command lookup continues to prefer canonical command outcomes, so it does not wait for audit. Route own-order, fill, trade, and current-market reads to the operational store only after their own coverage proofs; route mixed order/trace/event-list reads to a new audit store **only after** both source classes and their ordering are proved there. A componentwise minimum of operational and venue-audit partition frontiers is a necessary bound, **not sufficient** for an individual order: build the set of all source members affecting that order, including maker-side fills and direct events, then prove both stages cover that dependency set. A combined read also needs a stable as-of token and filtering that returns only facts at or before the proved prefix. Never combine a newer order state with an older event trail while labelling the whole response fresh. Return existing source/lag metadata and apply the current route's freshness/error behavior; do not silently change a public route or promise stronger consistency than the old one. Cross-database reads do not share an MVCC snapshot; keep a combined read on the legacy store until the token and route-specific parity are proved. Market freshness additionally needs a committed operational prefix and a drained/covered market queue; an empty unlogged queue alone is not proof after restart.

**Backpressure and recovery.** Preserve `control-room-fresh` versus `venue-core` policy. Control-room freshness samples both stage lags plus lifecycle/market coverage; venue-core continues to report projection lag while gating durable worker lag. In either mode, reject *before* durable ingress if finite canonical retention, disk, or replay horizon would be exceeded; never emit 202 until durable acceptance itself is acknowledged. A stalled audit stage is an explicit full-pipeline failure, not permission to call operational-only throughput “full.” On crash, recover each stage from its last committed contiguous canonical frontier and D-055 claim; ambiguous commits must read completed claims rather than reapply effects. Rebuild unlogged dirty queues from canonical/frontier gaps after PostgreSQL restart and invalidate freshness proofs across postmaster generations until verified. Permanent hash/content mismatches quarantine the member, alert, and stop that partition's frontier; no skip, overwrite, or dead-letter-and-advance. Transient serialization/deadlock retries remain bounded by the immutable retry deadline. Failed projection writes do not undo canonical acceptance; they create visible lag and backpressure.

**Placement and rollout.** Keep canonical tables in canonical Postgres. If the split gate passes, build operational and venue-audit **isolated versioned shadow tables** with distinct claims/frontiers in the existing projection instance; never have old and new workers write the same effect tables. Co-locate any direct-audit source with its current mixed table in the database used by `projectionConnection()` and retain legacy mixed reads until complete migration is verified. A separate audit PostgreSQL **instance**, with its own WAL/storage budget, is a later topology experiment; a second database in the same instance shares core I/O resources. Replicate/replay the direct source to that audit instance and advance its frontier only after destination commit; the source remains authoritative through ambiguous commits. Preserve local Compose single-instance support. Compare shadow full rows and frontiers, then switch individual read adapters only after parity. Prove merged venue/non-venue order before switching any mixed timeline route. Retain old full projector and read routing through rollback, but account for the resource cost of temporary shadows in measurement. Rollback routes to the old projection only if its frontier is current; otherwise replay old venue projection from canonical authority and direct events from their durable source before declaring rollback complete. Version epoch and migrations; do not rewind a watermark in place or reuse a stage name for different effects. Retire old tables only after a separate retention/rebuild decision.

## Revised implementation and measurement sequence

Use the C43 fixture and frozen 300s/10k-offered profile as the comparison template: six materializers, 16 projector owners, 64 instruments, database settings, observer cadence, read load and fixed collection points. Preserve the exact source/image/configuration manifests; record every hardware, code, cohort and timing difference. C43 raw evidence is host-local, so first verify availability rather than reconstructing missing detail from ledger aggregates. Each material treatment receives focused fault/parity tests and one fresh, matched, full-pipeline control/treatment diagnostic when resource authorization exists. A diagnostic failure remains in the ledger. No new load or infrastructure was needed to make this research decision.

0. **Authority and measurement preflight.** Inventory every venue, direct admin, protective and compatibility event producer and every order/trace/global reader. Verify which legacy rows have trustworthy provenance and whether canonical outcome plus retained command metadata reproduces all event fields. Freeze the existing full-profile checker. For a proposed split, add a separately versioned stage-vector report to `stress.mjs`, `do-benchmark-check.mjs`, and the headroom helper; prove synthetic omissions, duplicates, gaps, stale epoch/generation, foreign source, ahead/behind stages and direct-event omissions fail. Bind each stage to the **same closed accepted venue-member set**, checked by exact per-partition intervals and checkpoint snapshots; non-venue events use their own source membership. Never sum stage counts, compare two nonsimultaneous counters as a causal rate, or equate final drain equality with in-load freshness. Validate instrumentation perturbation by the existing rule. **Go:** old checker unchanged and new known-good/bad fixtures classify correctly. **No-go:** unknown source membership or unaccounted observer cost; no capacity claim.
1. **Replay and causal proof before tuning.** In the existing full path, make event-ID replay compare header, typed facts, payload and assigned sequence; preflight novel legacy/direct IDs before allocating trace sequences. Test identical and changed retries, concurrent absent IDs, mixed traces, missing payloads, ambiguous commit, and D-055 rollback. Build a canonical ordered effect inventory covering submit/reject/cancel/modify, maker and taker fills, trades and direct events; prove per-order source dependencies across partitions and compare all lifecycle numeric/text/terminal fields to a quiesced reference. **Go:** deterministic business, event and trace parity on fresh, aged and restart fixtures; every unclassifiable legacy row remains on the old read path. **No-go:** collision skip, trace gap or unproved cross-partition causality.
2. **Diagnose and trial the cheapest work reduction with the full path intact.** A fresh C43-shaped concurrent control captures same-prefix residence, lock/wait time, CPU/I/O, WAL/rows/index bytes, and lifecycle/market coverage. Select *one* measured lever: safe normalized write reduction, payload duplication reduction **only after source equivalence**, or a per-order lifecycle accumulator maintained in an isolated shadow. First compare exact rows/replay and lock contention; then run a matched 300s treatment under the full pipeline, same read load and fresh fixture. **Go:** exact cohort/rebuild/route parity, no added acceptance work, improved full-pipeline freshness and enough measured margin to justify retention. **No-go:** only stage-local improvement, increased hot-row contention/WAL without full-system benefit, or a changed retention contract. If this satisfies the final gate, stop; a worker split is unnecessary.
3. **Select or reject the split on evidence.** If step 2 still fails and the control shows material audit work delaying operational commits, prove lifecycle no longer depends on audit rows and trial isolated versioned operational/audit shadows on the existing projection instance. Stage claims, effects and contiguous watermarks commit atomically under D-055 with one writer per effect set. Preserve legacy mixed reads and source; no direct journal is needed merely to time the venue split. Run one fresh matched full-pipeline diagnostic, counting both stages, lifecycle, market, total WAL/rows, lag and resource use. **Go:** operational freshness improves and venue audit also meets its own exact cohort/freshness gate without worse shared-resource pressure; rollback catch-up is demonstrated. **No-go:** only operational pass, audit backlog growth, cross-stage causal gap, or same-instance contention that erases the gain.
4. **Move reads or placement only for a measured need.** If a mixed audit read must move, first prove direct-event provenance, a lossless ordered change source, merged route pagination/order and failure semantics; add a same-transaction journal only if an existing-table change feed cannot provide that proof. If venue payload writes dominate, trial a locator only after exact event reconstruction and retention/point-read tests. If physical I/O remains limiting, compare a separate audit instance under both fixed total resources and a separately labelled larger resource budget. Each change gets a fresh matched full-pipeline diagnostic and its own rollback proof. **No-go:** unclassifiable historical rows, cross-store read without stable as-of token, unrecoverable locator, or hidden resource increase.

**Final promotion, after the last material change.** Qualify the final image and configuration under prescribed read load, warm and aged state, full reference/rebuild, trace and replay parity, crash/ambiguous-commit recovery, bounded lag and conservative command-weighted 5s lifecycle/10s market/30s tail freshness checks. At a frozen **closed-cohort** measurement boundary, accepted/direct-acked/materialized counts and each required projection stage's exact member interval/frontier must agree for that cohort; stage snapshots need collection timestamps or a read barrier and may not be substituted with later postdrain counts. For a split, venue operational and audit stages must each cover the same venue cohort; direct-event authority is checked against its own source cohort and mixed route parity. Retain frozen retry/deadlock and sampler limits. Run the established **three separate stopped-source fixed-backlog drains at ≥20% measured rate headroom** and also prove sustained in-load backlog/freshness under concurrent intake; the former alone is not a 20% concurrent reserve claim. Record every run, failed setup and correction in the ledger without rewriting C43. A miss in any required stage or drain is a failed qualification, even if an operational-only diagnostic looks good.

## Assumptions and open decisions

- The canonical outcome plus retained command metadata can reproduce every venue-generated event's payload and trace fields. This must be proved before audit locator storage or shorter retention; older compatibility batches may require immutable backfill.
- Current per-instrument lane ownership is sufficient for both sides of each fill. Verify actual cross-partition order touches; if present, specify deterministic order-key sequencing before incremental lifecycle.
- The current `runtime_events`/payload tables are rebuildable read projections for venue outcomes but remain durable source material for direct admin and protective-control events until a separate lossless source and migrated read path are proved. Post-trade canonical event history and public audit requirements may have different ownership and must not be pruned by this plan.
- C43's full-pipeline gap is small in *rate* but has no proven 20% drain headroom or concurrent reserve; a merely 0.1–1% improvement is not the target. The point where PostgreSQL write/WAL contention or lifecycle recompute becomes the limiter after any treatment is unknown.
- Decide the retention/replay horizon, combined-read consistency token, audit-instance resource budget, and measured read-latency SLO before cutting over. If those choices cannot preserve current API behavior, keep the legacy full read path while still measuring the shadow projection.
