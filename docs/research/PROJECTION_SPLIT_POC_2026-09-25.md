# Projection split POC — 2026-09-25

Status: disposable experiment complete; no production rollout or throughput qualification.

## Decision question

Can independently checkpointed venue timeline and command-status workers keep the full normalized projection current at 10,000 accepted commands/s for 300 seconds, while preserving exact lifecycle and event state? This trial tests the smallest existing seam: `ProjectionStage.Timeline` and `ProjectionStage.CommandStatus` already have separate SQL paths and D-055 claim identities. It uses one projection PostgreSQL instance; it does not test added physical I/O capacity.

## Attack plan

1. Start a timeline worker and a command-status worker for each existing projector owner. Use distinct watermarks and batch claims. Cap each status partition at its committed timeline frontier because lifecycle refresh reads timeline facts. Leave canonical materialization, direct admin events and public read routes as they are. **Local gate:** exact fresh, replay and interleaved lifecycle/market business rows versus the full reference; no missing event or frontier gap.
2. Run a short local load using the existing venue-event materializer stress path. Capture offered, accepted, direct-acked, materialized, each stage's closed-cohort projected count and frontier, HTTP p95/p99, in-load lifecycle/market freshness, lag, retries, WAL/rows and postdrain reference. **No-go:** any parity or ordering miss, stale or unknown stage cohort, unbounded lag, or projector failure. Stop before hosted load if this gate fails.
3. If local gate passes and credentials/harness are usable, run one disposable DigitalOcean C43-shaped full-pipeline control and one treatment, 10k offered/s for 300s each, on fresh equal c-32 fixtures. Preserve images, source/config manifests, commands, raw reports, failed attempts and collection timestamps. Destroy only the droplet created for this POC after evidence capture. **Diagnostic go:** exact same closed source cohort in both stages, lifecycle and market parity, better in-load freshness without worse combined WAL/CPU/I/O or lag. **Qualification gate:** frozen full-pipeline checker, sustained in-load freshness, and three separate stopped-source drains at at least 20% headroom; postdrain equality alone never qualifies.

## Comparison boundary

- C4/H4: sustained full-projection accounting at about 2,500/s for 300s; current strict downstream freshness was unproved.
- C5/H1: about 10,000/s canonical venue materialization for 300s with projections disabled; not a full-pipeline comparator.
- C28: 10k offered, 300s, c-32, four materializers, 16 projector writers; final counts caught up but lifecycle/market bounds 6,314/7,315ms failed.
- C43: c-32, six materializers, 16 projector owners, 10k offered for 300s; 2,992,504 accepted/direct-acked/materialized at the source snapshot, later 2,967,975 projected with 26,029 lag. HTTP p95/p99 78.06/122.08ms. Frozen full-pipeline and freshness checks failed; postdrain reference matched. Source/projector snapshots were not simultaneous.

Trial changes worker scheduling and stage identities. Unless the hosted control matches code, topology, fixture, image, hardware and observation cadence, comparison remains descriptive rather than causal. Stage counts must never be summed.

The control checker failed sustained downstream freshness. Its first checker attempt also missed a diagnostics symlink; the original log was preserved, the symlink added, and the checker rerun with the pinned 10k gate settings. The final control checker fails only freshness. The split checker fails projected lag, materialized/projected gap, downstream cohort authority, and freshness. In the split arm, stage markers did not cover the frozen exclusive cohort and final dirty queues were not drained at that observation; no lifecycle or market latency estimate from that cohort is valid. The split arm also reported a later 16-owner direct status vector with 2,999,950 status and 2,999,950 timeline projections, matching partition frontiers, and zero lag. That later catchup does not change the frozen failure. Counts and lags in the table are separate collection snapshots, not one atomic database view.

Both postdrain proofs passed contiguous source sequence and exact projection frontier checks. Control rollback-only reference matched 2,471,228 lifecycle rows and 64 market rows; split matched 2,471,664 lifecycle rows and 64 market rows. Projection WAL deltas at report collection were 17.20 GB control and 16.99 GB split, but split had outstanding work at its frozen snapshot, so these are not comparable completed-work costs. No CPU or I/O efficiency claim follows. The split did not improve sustained full-pipeline service or qualify at 10k/s. Stop at this no-go; three drain-headroom trials were not run.

Local and hosted runs support narrow stage correctness and eventual business parity. They do not support production rollout, strict in-load freshness, cross-partition maker causality, or drain headroom. This split reads canonical candidates in both stages on the same projection PostgreSQL instance; keep it disabled by default. Next work should follow the structural work-reduction option in the decision memo, with a new matched test before revisiting stage separation.
